## 3. The IVT layer is derived from the AR paint, not from IVT (report B's real bug)

`ewb_live/viz/exceedance.py`: `class_plane = ivt_class_plane(ivt_day[i], ar_paint)`
with `ar_paint = ar[i] & ~bridged[i]`, and `ivt_class_plane` writes 0 outside its
mask argument. `dashboard/mergedmap.js` then colours the AR layer *only* from
that plane and reads it for hover (`ivtAt`). Verified on the published frames:
the `.ivt` non-zero mask is **cell-identical** to the `.bin` AR plane for every
frame checked (single exception `2026081512`, 577 cells — the gap-bridge
footprint, which is intentional).

Consequence: there is no IVT field on the map — there is an AR-mask field with
IVT bins looked up inside it. Any screen, any marginal-threshold flicker of the
|∇²IVT| ≥ 2.5 test, and any seam/crop loss deletes the "IVT values" too, even
though IVT ≥ 400 is unchanged. The link-cap/centroid-screen fix does not touch
this: after it, IVT still vanishes wherever the AR mask does not paint.

Fix: compute the class plane from the IVT field itself (`ivt >= 250`, the first
bin edge) and keep the AR bit only as a paint/legend gate; publish the mask
state as a separate flag (the `bridged` plane already shows how).

## §7 Correction: the §2 box numbers were measured 180° away

`probe.py` and the first probes indexed the merged map with
`col = (lon % 360) * 4`. The merged map runs **-180 → 180**, so the correct index
is `col = (lon + 180) * 4`; the old formula looks up `lon + 180`. Every
basin-scoped number in §2 (and the "expected" values in the verification recipe
above) is therefore a measurement of the antipode:

| label used | longitude actually measured |
|---|---|
| "south Atlantic (-25W, 20E)" | 96W – 85W — Caribbean / Gulf of Mexico |
| "north Atlantic (70W, 5W)" | 110E – 175E — Philippine Sea, i.e. **Typhoon PEILOU** |

That is why a typhoon kept showing up in "north Atlantic" attributions. The
physical probe (`/tmp/ivt_probe.py`) used the ERA5 0-360 axis correctly and is
unaffected — the *diagnosis* (mask present, nothing painted) came from it and
stands. The corrected box numbers are §8.

Report B (north Atlantic 08-12 18Z → 08-13 00Z) is fixed twice over: the AR layer
paints, and the IVT layer now carries every cell with IVT ≥ 250 (7 635 – 8 470 in
the box) whether or not an AR is painted there, so "IVT values disappear" cannot
recur. The 08-14/15 zeros are report C's remaining cases, with two distinct causes:

1. **north Atlantic 08-14 18Z, 08-15 00Z — a globe-spanning "track" killed by one
   typhoon.** The ledger names it: `ar_20260813T18_107`, 150 691 cells over 7
   steps, bbox lat[0, 51.25] **lon[-180, 179.75]**, reason `tc`, PEILOU at 0.0 km,
   `tc_steps` = all 7. Every step is inside the storm because the track's cells
   *are* the storm's cells plus the whole northern-hemisphere moisture band. The
   step-level TC rule cannot help a track whose every step is hit.
2. **south Atlantic 08-13 00Z, 08-14 18Z — deleted before tracking, no ledger
   entry.** No dropped track overlaps the box at those steps and no step-TC screen
   fired; the AR mask itself is empty there. Cause: the detector's floors
   (`>= 500 cells`, `|mean lat| > 15`, applied per *component*) run over
   **longitude-periodic, time-linked** components, and the tropical/subtropical
   IVT band connects across the antimeridian, so a real mid-latitude AR is merged
   into an object whose mean latitude is near the equator. The whole object fails
   the floor and every AR inside it vanishes silently.

Single-frame measurement of that floor (`/tmp/floors_probe.py` on the box,
2026-08-12 06Z, one frame, periodic labelling):

```

  ...of which |lat| > 15:            50 185 cells
kept by the object floors                0 cells   <- yes, zero
kept by a 41x41 neighbourhood |lat| rule 49 911 cells (67% of raw)
```

and across the whole published window, per frame globally:

```
frame        painted AR cells   IVT>=250   IVT>=400
2026081200            28 066      204 939     77 017
2026081300            13 817      197 051     67 598
2026081418            13 118      194 380     72 404
```

So the lane publishes 13k–28k AR cells a frame where the detector's own raw mass
above |lat| 15 is ~50k: **the object-level tropical exclusion is throwing away
roughly two thirds of the physically-detected AR mass, unevenly, basin by basin**
— which is exactly the "an AR just disappears" signature, and it is invisible in
the ledger because it happens before tracking.

Two candidate fixes were tried. `notes/ar_ring_split_option.patch` splits any
component spanning > 200° of longitude at the seam before the floors; it recovers
the south Atlantic (25 937 → 107 647 kept cells in the box over the window) but it
also lets through hemispheric arcs that are moisture bands, not ARs, so it is
**not landed** — it is here as the measurable option. The version that matches the
physics is to make the tropical exclusion **local** (a cell is kept when the mean
|lat| of its detector neighbourhood exceeds 15°, ~3× denser AR layer, no
whole-AR disappearances). That changes detector semantics, the event list and the
scores, so it is an owner decision, not a bug-fix sprint. Both keep the
documented purpose of the seam work (a Greenwich-straddling AR is one object).
